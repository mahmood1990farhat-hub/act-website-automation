## Small integration change
The managed route invokes a small adapter only when the tested stop service
returns `created=True`. Both repeated and simultaneous requests therefore select
one request for this follow-up. Legacy fallback remains untouched; it already
performs its own notifications and must not receive a second path.

The adapter reloads and verifies the committed cancelled Trip and case, calls the
existing PDF helper, then calls the existing passenger and internal email helpers.
No new email/PDF template or notification platform is created. No replacement
refund wording is injected into the preserved multilingual renderer.

The original PDF helper saves the whole Trip through FileField.save(save=True).
The adapter prepares it under the Trip row lock so a stale object does not overwrite
concurrent refund metadata. Email calls take place after that transaction closes.
The PDF remains a cancellation receipt, not a constantly rewritten refund ledger.
A provider outage does not prevent requesting the cancellation receipt. A PDF
failure leaves the journey cancelled, flags follow-up and avoids sending a
passenger a fallback link masquerading as the requested PDF; internal notification
is still attempted. A sender fault cannot undo the cancellation.

## Explicit delivery boundary — do not overclaim
The preserved cancellation senders are asynchronous and do not return a definitive
SMTP result. `requested` means the existing function was invoked, NOT that SMTP
accepted it or that it arrived in the inbox. Some internal errors are handled by
the preserved sender itself. This patch does not change that established behaviour.

This is request-level duplicate suppression, NOT an exactly-once email outbox.
A process crash after the durable cancellation and before all follow-up completes
can leave an incomplete notification. A repeated cancellation deliberately does
not blindly resend after uncertain delivery. There is no scheduled retry, new queue,
auto-resend, claimed delivery timestamp or invented SMTP acceptance. Targeted manual
recovery must inspect existing evidence; reliable durable retry/acknowledgement can
only be added as a separately reviewed change if required. Do not call this helper
from review/refund webhooks to resend the original cancellation receipt.

No customer-visible response asserts delivery. Initial cancellation and later
refund status remain distinct. The existing percentage policy, recorded receipt,
payment provider/accounting, permissions and review APIs are untouched.
